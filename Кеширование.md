# ⚡ Задача кэша - ускорить ответ, а не держать нагрузку

## 🔷 1. Кэширование - что это такое?

### 🔷 1.1 -> Сокращение response time сервисов

К примеру ускорить задержку между расстояниями сервисом и БД, тут либо можно в отдельный сервис хранить кэш либо рядом с основным сервисом "в зависимости от ресурсов компании", также в зависимости от размеров данных либо они попадают в оперативку при большой нагрузке, либо на диск HDD/SSD "тут уже как выберут"

### 🔷 1.2 -> Снижение лишней нагрузки на сторонние сервисы

Кеш спасает например БД от нагрузки и позволит немного невелировать эту нагрузку, для предотвращений проблем

### 🔷 1.3 -> Переиспользование ранее полученных или вычисленных данных

Чтобы решить проблему лишней нагрузки еще на уровне процессора, при тяжёлых каких-либо вычислений

### 🔷 1.4 -> Стабилизация работы при кратковременных отказах систем

Например в случае отказа работы стороннего сервиса, в системе понятное дело будут ошибки, но в случае кеша можно сымитировать работу неактуальными данными тем самым вместо кучи ошибок в системе, приложение не встанет а будет дальше работать

### 🔷 1.5 -> Основные термины в контексте

- **Cache miss** — промах кэша, запрошенный ключ не был найден в кэше
- **Cache Hit** — попадание в кэш, запрошенный ключ найден в кэше
- **Hit radio** — процент попаданий запросов в кэш, характеризует эффективность кэширование
- **Горячие ключи** — ключ, на который приходится большая часть запросов
- **Прогрев кэша** — процесс наполнения кэша данными
- **Инвалидация** — удаление кэшированных данных

### 🔷 1.6 -> Какие данные кэшировать?

| | Частота изменений | Комментарий |
|---|---|---|
| 🟢 | Меняются часто (секунды) | кэширование чаще всего бессмысленно, но иногда может пригодиться |
| 🟠 | Меняются нечасто (минуты и часы) | чаще всего здесь задаемся вопросом — стоит ли мне кэшировать? |
| 🔴 | Меняются редко (дни, недели, месяцы) | в данном случае можно спокойно кэшировать эти данные |

### 🔷 1.7 -> Кэширование ошибок

> Кэшируем ошибки, и тогда последующие запросы не будут обращаться к источнику информации, а также не будет cache miss attack "пункт 1.5 🔷"

## 🟡 2. Всегда ли кэширование полезно?

### 🟡 2.1 -> Эффективность

> AverageTime = DBAccessTime * CacheMissRate + CacheAccessTime

Пусть:
- DBAccessTime = 100ms
- CacheAccessTime = 20ms

Тогда при CacheMissRate > 0.8 - кэш вреден!

## 🟪 3. Виды кэширования

### 🟪 3.1 -> Внутреннее кэширование

> Это когда кэш рядом с сервисом лежит, на диске или оперативки

#### Плюсы:

- **Высокая скорость**

- **Отсутствие сетевых запросов**

- **Нет расходов на Marshaling/Unmarshalling данных**

#### Минусы:

- **Горизонтальное масштабирование**

- **Прогрев кэша перед падения сервиса**

---

### 🟪 3.2 -> Внешнее кэширование

> Это когда есть сторонний сервис, который хранит кэш

#### Плюсы:

- **Хранение большого обьема данных**

- **Простое горизонтальное масштабирование**

- **После падения сервиса данные кэша не теряются**

- **Простой прогрев кэша и простая логика инвалидации**

#### Минусы:

- **Скорость работы**

---

## 🟢 4. Способы взаимодействия с кэшем, стратегии

### 🟢 4.1 -> Cache Aside (кэширование на стороне)

> В этой стратегии, приложение координирует запросы в кэш и БД и само решает, куда и в какой момент нужно обращаться

---

### READ Aside

#### Шаги:

- **1. читаем из кэша**: Service -> Cache
- **2. Если даных нет**: Cache -> Service
- **3. Читаем из БД**: Service -> Database
- **4. Получаем данные**: Database -> Service
- **5. Сохраняем данные в кэш**: Service -> Cache

> Преимущества: сервис полностью контролирует логику кэширования, простая реализация, независимость от инфраструктуры кэша (если он упал, просто ходим напрямую в БД)

> Недостатки: при каждом промахе кэша сервису нужно делать два обращения (в кэш и в БД) и самому писать логику записи в кэш — больше кода на стороне приложения

---

### WRITE Aside

#### Шаги:

- **1. Сохраняем в БД**: Service -> Database
- **2. Получаем ответ**: Database -> Service
- **3. Сохраняем в кэш**: Service -> Cache

> Преимущества: запись быстрая, так как идёт напрямую в БД без промежуточных шагов

> Недостатки: есть окно рассинхрона между БД и кэшем — если между шагом 1 и 3 кто-то прочитает кэш, получит устаревшие данные; если шаг 3 (запись в кэш) упадёт, кэш и БД разъедутся

### 🟢 4.2 -> Cache Through (сквозное кэширование)

> В рамках этой стратегии все запросы от приложения проходят через кэш

---

### READ Through

#### Шаги:

- **1. Сначало читаем из кэша**: Service -> Cache
- **2. Если даных нет, читаем из БД**: Cache -> Database
- **3. Получаем данные**: Database -> Cache
- **4. Сохраняем в кэш и отдаём данные**: Cache -> Service

> Преимущества: сервис не знает ничего про БД, сервис работает только с кэшом, логика приложения намного проще

> Недостатки: если кэш упадёт то моё приложение в итоге будет не доступно

---

### WRITE Through

#### Шаги:

- **1. Сначало пишем данные**: Service -> Cache
- **2. Сохраняем в БД**: Cache -> Database
- **3. Получаем ответ**: Database -> Cache
- **4. Сохраняем в кэш и отдаём ответ**: Cache -> Service

> Преимущества: данные в кэше и БД всегда синхронны, при чтении никогда не будет устаревших данных, cache miss практически исключён

> Недостатки: запись становится медленнее (пишем в два места), при падении кэша приложение так же не сможет писать данные

### 🟢 4.3 -> Cache Ahead (опережающее кэширование)

> Запросы на чтение всегда идут только в кэш, никогда не попадая в БД напрямую

---

#### Шаги:

- **1.1 Чиатем из кэша**: Service -> Cache
- **1.2 Отдаем данные**: Cache -> Service
- **2.1 Периодиески загружаем данные из БД**: Cache -> Database

> Преимущества: чтение всегда максимально быстрое (только кэш, без обращения к БД в моменте запроса), нагрузка на БД предсказуемая и равномерная (не зависит от количества запросов сервиса)

> Недостатки: данные в кэше немного устаревшие (зависит от периода обновления), нужен отдельный фоновый процесс, дорого по ресурсам — грузим в кэш и то, что никто не запрашивал, больше расход оперативки, если процесс обновления упадёт — данные тихо устаревают

### 🟢 4.4 -> Резюме

- **Важно учитывать актуализацью данных**

- **Стоит балансировать между характером нагрузки**
> (какая нагрузка преобладает - чтение или запись)

- **Также не забыть про отказоустойчивость**
